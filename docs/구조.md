## 흐름

1. 운영자가 `src/content/posts/<글>.md` 를 쓰고 `main` 에 push
2. `.github/workflows/deploy.yml` — `npm run check` 실행
3. `src/content.config.ts` — 글 머리말 검사(종류·상태·사례 글 캡처). 어기면 빌드 실패 → 배포 안 됨 → Actions 실패 메일
4. `src/lib/posts.ts` `getPublished()` — `published` 만 최신순으로 각 페이지에 넘김
5. `src/pages/**` 가 정적 HTML 을 `dist/` 에 생성 → `scripts/check-dist.mjs` 가 완료 조건 점검 → GitHub Pages 배포

DB·API 없음. 방문자는 미리 만든 HTML 만 받는다.

## 폴더별 책임

- `src/content/posts/` — 글 1편 = 파일 1개 (운영자가 쓰는 유일한 곳)
- `src/story.md` — 나의 스토리 요약 4줄(머리말)과 전문(본문)
- `src/data/brands.ts` — 첫 화면 하위 브랜드 칸 (운영 중인 것만)
- `src/lib/` — 글 꺼내기·종류 이름
- `src/layouts/`, `src/components/` — 공통 틀, 머리줄, 연락, 글 목록 부품
- `src/pages/` — 화면 S01~S05 (화면ID 는 `docs/기획/` 기능정의)
- `tests/fixtures/posts/` — 점검 빌드 전용 글(초안·내림·빈 종류 확인용). 실제 사이트에는 안 나간다
- `scripts/check-dist.mjs` — 빌드 결과 점검
- `docs/기획/` — 요구사항·기능정의·개발계획·나의스토리

## 배치 규칙

- 새 글: `src/content/posts/` 에 `.md`. 머리말 `title, kind(case|tried|howto), status(draft|published|unpublished), date, summary, captures[]`. 사례 글은 `## 누구의 어떤 업무 / 전 / 무엇을 만들었나 / 후 / 비용과 기간` 제목 순서를 지키고, 캡처는 "무엇을 만들었나" 절 안에 R2 링크로 넣는다
- 새 화면: `src/pages/`, 공통 부품은 `src/components/`
- 새 하위 브랜드: 주소가 열린 뒤 `src/data/brands.ts` 에 한 줄
- 새 점검: `scripts/check-dist.mjs` 에 assert 추가. 점검 빌드에만 필요한 글은 `tests/fixtures/posts/`
